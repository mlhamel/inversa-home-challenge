# Playbook: run a historical data backfill

How the datalake gets its rolling 7-day history, how to trigger it on demand,
and how to read the outcome. Everything here reflects the deployed setup in
`infra/main.tf` and the ingestion module (`services/ingestion`).

## How refreshes happen today

| Piece | Detail |
|---|---|
| Job | Cloud Run Job `ingestion-job` — runs `python -m inversa.ingestion.backfill` |
| Window | fixed 7 days (`BACKFILL_DAYS = 7` in `backfill.py`) — FIRMS day ranges, OpenAQ `/sensors/{id}/hours` history, Open-Meteo `past_days=7` |
| Output | ZSTD Parquet written to the datalake GCS bucket, GCS-mounted at `/mnt/data` (`DATA_DIR`) — the same files `web-api` reads through DuckDB |
| Schedule | Cloud Scheduler `trigger-ingestion`, `0 */2 * * *` UTC — prod self-refreshes every 2 hours |
| Timeout | job `timeout = "1200s"` (worst case ~20 min per run) |

## Trigger a manual run (prod)

```sh
gcloud run jobs execute ingestion-job \
  --project inversa-home-challenge \
  --region northamerica-northeast1 \
  --wait
```

`--wait` blocks until the execution finishes (up to ~20 min). Each run
rebuilds the full 7-day window and rewrites the lake files; it is safe to run
while the API is serving because readers open the parquet through fresh
DuckDB cursors.

Alternative trigger path: the deploy workflow (`.github/workflows/deploy.yml`)
has a `refresh datalake once` step that executes the same job whenever
`FIRMS_MAP_KEY` and `OPENAQ_API_KEY` are configured — so `gh workflow run`
re-deploys *and* refreshes the lake in one shot.

## Local equivalent

```sh
FIRMS_MAP_KEY=... OPENAQ_API_KEY=... make backfill   # writes ./.local_datalake
make serve                                           # API + UI off the local lake
```

## Read the outcome (log forensics)

```sh
gcloud logging read \
  'resource.type="cloud_run_job" AND resource.labels.job_name="ingestion-job" AND timestamp>="2026-11-18T21:29:00Z"' \
  --project inversa-home-challenge \
  --limit 800 \
  --format "value(textPayload)"
```

What to grep for:

- `nasa_firms:` / `open_meteo:` / `openaq: station <id>: N rows, M rejected` —
  harvested rows per source/station.
- `HTTP 429 ... retrying` — OpenAQ free-tier throttling. **`0 rows` for a
  station usually means the request was rate-limited, not that the station
  has no data.** Current pacing (`CONCURRENCY = 5`, `1.1 s` interval) trips
  the limiter in bursts; a follow-up should serialize OpenAQ harder and honor
  `Retry-After` deeper.
- Task-level errors appear as `ERROR` lines; retry exhaustion shows the
  final attempt status.

## Validate the lake through the API

Resolve the current service URLs first (they are generated by Cloud Run):

```sh
API=$(gcloud run services describe web-api --project inversa-home-challenge --region northamerica-northeast1 --format 'value(status.url)')
UI=$(gcloud run services describe web-ui --project inversa-home-challenge --region northamerica-northeast1 --format 'value(status.url)')
```

Direct (the API needs query params):

```sh
curl -sG --data-urlencode "start=2026-11-12T00:00:00Z" \
        --data-urlencode "end=2026-11-18T21:00:00Z" \
        "$API/api/timeline/summary"
curl -sG --data-urlencode "timestamp=$(date -u +%Y-%m-%dT%H:00:00Z)" "$API/api/snapshot"
```

Through the web-ui proxy (what the browser hits):

```sh
curl -sG --data-urlencode "timestamp=$(date -u +%Y-%m-%dT%H:00:00Z)" -o /dev/null -w '%{http_code}\n' "$UI/api/snapshot"
```

Expect `200` and growing data coverage in the buckets after each successful
run cycle.
